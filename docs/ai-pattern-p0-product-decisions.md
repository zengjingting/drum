# EasyInput AI 鼓机 P0：产品决策与体验设计记录

日期：2026-08-30  
状态：实现和真实 API 页面验证完成；真机同步与播放验收待用户连接设备确认

## 1. 本阶段要闭合的问题

首版只验证一条可演示的 AI 硬件价值链：用户用中文描述节奏，模型给出当前硬件能播放的六轨 16 步 Pattern；用户点击“应用”将候选放入已有音序器，再用原有“开始”按钮控制播放。这里必须区分模型生成、应用到编辑器、硬件同步和开始播放四种结果。

本阶段明确不做录音、Audio-to-MIDI、AI 解释实体 Pad Pattern、多 Pattern A/B、灯效、音色生成或思考模式实验。这些方向有价值，但会把模型、音频理解、存储和灯光体验同时带入，无法快速验证文字生成鼓点这一核心假设。

## 2. 决策过程与依据

### D1：使用 DeepSeek V4 Flash，首版关闭 thinking

- 输入输出是约束明确的结构化节奏生成，不要求模型进入实时音频链路。
- 模型选型实验已比较三个候选，并综合自动约束分、人工听感和响应速度选择 DeepSeek V4 Flash；详细证据与结论见 `ai-pattern-model-selection-decision.md`。
- P0 沿用实验中已验证的非思考模式，避免在产品实现阶段改变实验条件。思考模式是否提升听感是未验证假设，不在本阶段补做。

### D2：模型调用放在本地代理，不从浏览器直连

- 浏览器直连会暴露 API 密钥，也难以统一实现错误脱敏和校验。
- 本地代理仅监听 `127.0.0.1`，密钥只读取 `DEEPSEEK_API_KEY`；前端 bundle、响应、日志和测试快照都不包含密钥。
- 模型调用仍然需要网络，但它只影响“生成”动作，不参与 I2S、96 PPQN 或硬件播放时钟。

### D3：复用评测 Harness 的合同，不另造一套产品格式

- 产品输入复用当前硬件事实：固定六音色、4/4、16 步、40–240 BPM、每格开/关。
- 模型输出必须是 `easyinput.pattern.v1`；服务端复用评测 Harness 的请求默认值、提示词、Schema 校验和 Mask 顺序。
- 通过服务端校验后，网页仍执行第二次防御性 Schema 校验，并独立复算六个 Mask；服务端 Mask 与网页复算不一致时禁止下发。
- 该设计让“模型评测的通过条件”和“产品可写入硬件的条件”保持同源，减少实验结论与实现之间的漂移。

### D4：只允许一次针对校验错误的修复，并保留首答失败

- 首答合法时直接形成候选；首答不合法时，只把校验错误和首答交给模型修复一次。
- 修复后仍不合法则终止，不能把错误 Pattern 送入硬件。
- 产品响应保留 `firstPass.valid/errors` 与 `repairAttempted`，页面会提示“首答失败后已修复一次”；修复成功不能改写首答失败事实。
- 一次修复在成功率、响应时长和可解释性之间形成清晰边界，避免无限重试掩盖模型能力。

### D5：只保留一个 16 步编辑器，生成、应用和播放分成三个动作

- 生成完成只展示名称、风格、BPM 和设计说明，不改变主音序器，也不再绘制第二套只读音序图。
- “应用”按钮在候选生成后即可使用，不依赖串口连接。点击后才把六轨 Mask 填入已有的 16 步音序器。
- 设备在线时，应用沿用原音序器的原子 `PATTERN` 同步链路并等待 ACK；设备离线时先完成网页内应用，连接后自动同步。
- “应用”不发送 `TOGGLE`。播放由既有“开始/停止”按钮负责；应用成功后的手动改格继续复用原有实时同步链路。
- 这项交互是在真实页面试用后修订的。初版的“双音序图 + 应用到硬件”让候选预览与实际编辑器割裂，而且把应用按钮错误地绑定到串口能力，导致离线时始终灰色。

### D6：硬件同步以 ACK 为准，播放状态由独立 Transport 控制

应用事务按以下顺序执行：

1. 将候选转换成固件顺序的六个 16-bit Mask，并立即填入网页主音序器。
2. 如果设备离线，标记为待同步；页面明确提示连接设备后同步，不声称硬件成功。
3. 如果设备在线，确认协议 v2 声明 `pattern`、`sequencer` 能力。
4. 如 BPM 不同，发送 `BPM <value>`，等待设备 `STATE` 回报目标 BPM。
5. 发送单条原子 `PATTERN`，等待 `{"type":"ack","command":"PATTERN"}`；ACK 前不显示硬件同步成功。
6. ACK 后提示用户点击原有“开始”按钮。应用事务不会自动启动播放。

选择原子 `PATTERN` 而不是六条 `MASK`，是为了避免只更新到一半、串口响应穿插和连续协议错误。现有固件已支持这一协议，因此本阶段没有改固件，也不需要重新烧录。

### D7：错误分层，不把协议错误伪装成断线

| 层级 | 示例 | 页面行为 | 串口处理 |
| --- | --- | --- | --- |
| 模型/配置 | 未配置密钥、网络失败、供应商错误 | AI 区域显示安全错误，不出现原始输出或供应商详情 | 不影响串口 |
| 输出校验 | Schema 错误、修复后仍失败、Mask 不一致 | 禁止应用，保留首答状态 | 不写串口 |
| 协议 | `Unknown command`、ACK 超时、设备拒绝命令 | AI/音序器区域显示协议错误，不标记 USB 物理断线 | 端口保持在线，可由用户正常断开 |
| 传输 | 读写中断、物理拔线 | 显示重新连接，拒绝所有待确认事务 | cancel reader、释放 reader/writer lock、close port |

这解决了旧页面把 `Unknown command` 误当成连接失败、但 Chrome 仍占用端口的问题：协议错误不会改变在线事实；真正的读写错误会完整释放串口。

## 3. 体验状态机

AI 区域使用以下用户可见状态：

- `idle`：等待描述。
- `generating`：调用模型并校验，不能再次生成或应用。
- `ready`：候选元数据可见，主音序器仍保持原内容，“应用”按钮可用。
- `applying`：将候选填入主音序器；设备在线时继续设置 BPM、发送 Pattern 并等待硬件确认。
- `applied`：已填入主音序器；页面另外区分“网页待同步”和“硬件已 ACK”。这不表示已经开始播放。
- `error`：模型、网络、配置或校验失败。
- `apply_error`：串口、协议或 ACK 失败；候选 Pattern 仍保留，可在恢复连接后重试。

该状态机的关键产品边界是：`ready` 不改变主音序器；网页内 `applied` 不等于硬件成功；只有收到 ACK 才能声称硬件已同步；只有用户点击“开始”并收到运行状态后，才能声称开始播放。

## 4. 独立性与实时边界

- DeepSeek 只在生成阶段运行，浏览器只在确认阶段通过 USB 下发控制命令。
- Pattern 应用后由开发板 I2S 样本时钟和 96 PPQN 推进，AI、网络、浏览器都不参与实时播放。
- 网页关闭或网络断开后，开发板继续运行最后一次已确认的 Pattern。这是本项目作为硬件产品而不是网页播放器的核心边界。

## 5. 验收口径与当前证据

自动化已覆盖：

- 后端有效首答、一次修复、修复后失败、未配置密钥、供应商错误脱敏和健康检查。
- `easyinput.pattern.v1` 前端复核、六轨 Mask 复算、服务端/网页 Mask 不一致阻断。
- 生成后主音序器保持不变；“应用”可离线使用并填入唯一主音序器；应用代码路径不触发播放；硬件成功仍受 ACK、协议拒绝和超时门控。
- 原有评测 Harness 31 项测试，确保产品实现复用的 Schema、约束、Mask 和一次修复语义未回归。
- 原有 C 侧节拍、混音、编码器、鼓资源与协议合同测试。

仍需真机验收，不能用 mock 或单元测试替代：

真实 API 页面验证已经确认：候选生成前后主音序器内容不变；生成后“应用”可点击；点击应用后主音序器获得候选，而原有按钮仍显示“开始”，页面没有第二套 AI 音序图。

剩余真机验收：

1. 连接当前已烧录协议 v2 的开发板，生成候选并点击应用。
2. 确认 ACK 前不显示硬件成功，ACK 后六轨和 BPM 与主音序器一致，但硬件仍保持原运行状态。
3. 点击原有“开始”，确认硬件开始播放；再修改主音序器格子，确认硬件实时同步。
4. 播放中关闭网页或断网，确认硬件继续按最后 Pattern 独立运行。
5. 主动断开后重新连接，确认串口不会被浏览器遗留占用。

完成上述真机检查前，准确结论是“P0 实现、自动化合同和真实 API 页面交互验证完成”，不是“真机端到端已经验收”。
